## Redis credential handling

Run `python3 scripts/provision_redis_secrets.py secrets` locally only before a separately approved deployment. It creates an untracked password file `secrets/redis_password` (0600) and hashed ACL file `secrets/redis_acl` (0644), both inside `secrets/` (0700). ACL is read by Redis's container UID; do not make the plaintext password world-readable or put secrets in environment variables or CLI arguments. The Redis default user is disabled, while vns_worker is confined to the BullMQ key prefix bull:vns:*. The unauthenticated Redis healthcheck only confirms a NOAUTH reply; CI additionally checks authenticated PING, forbidden commands and namespace. Do not activate the `data`/`worker` profiles until durable BullMQ bookkeeping, PostgreSQL restore/persistence and separate operator approval are addressed.

## CI-only BullMQ retry, deduplication and worker-crash drill

The disposable Redis integration suite additionally checks that a retained BullMQ `jobId` prevents duplicate queueing, that a harmless probe can be retried after one simulated transient failure, and that a replacement worker can reclaim a stalled probe after its predecessor is forcibly killed. All jobs are test fixtures; no editorial side effects exist.

**Important:** BullMQ provides at-least-once processing. Reclaiming a stalled job may execute its handler again, so neither a unique Redis job ID nor these tests guarantees exactly-once video rendering, uploads or payments. Durable PostgreSQL-to-Redis enqueue bookkeeping, outbox reconciliation, side-effect idempotency, Redis persistence and recovery from simultaneous database/queue failures are still necessary before enabling production work. The test is not authorization to start data or worker profiles on the VPS.

## Transactional job outbox (`0002_job_outbox`)

Migration 0002 adds `vns.job_outbox` with one durable row per `vns.jobs` job and a deterministic BullMQ `jobId` of the form `job-<uuidwithoutdashes>`. The `SECURITY INVOKER` function `vns.create_job_with_outbox(kind, idempotency_key, story_id, max_attempts)` writes the business job and queue intent inside the same PostgreSQL transaction. Repeated requests with identical parameters return the same job UUID; conflicting reuse fails. Redis is never contacted inside the database transaction. The original `vns.jobs.kind` allowlist remains unchanged; test-only `probe` work is deliberately excluded from the persistent editorial ledger.

The new ledger is a **delivery intention**, not a claim of exactly-once delivery. A future reconciler must commit a job with PostgreSQL, then enqueue with its stable BullMQ job ID, and mark the outbox row `enqueued` only after Redis acknowledges it. Redis loss, process crashes between enqueue and status update, and already-completed jobs require careful reconciliation and idempotent downstream side effects; those controls are not deployed yet. Queue submission still has no API route and must remain behind authenticated admin authorization in a later step. Migration 0002 is exercised by reversible migration tests and the disposable PostgreSQL backup/restore drill. Do not apply it to VPS without explicit data/backup approval.

## PostgreSQL-to-Redis outbox reconciler (Git-only)

A separate `apps/worker/src/dispatch.ts` process refuses startup unless explicitly enabled with `VNS_OUTBOX_DISPATCH_ENABLED=true`, `VNS_WORKER_ENABLED=true` and correctly mounted PostgreSQL/Redis password secrets. No running Compose service launches it. It selects at most ten pending or already enqueued nonterminal editorial jobs with `FOR UPDATE ... SKIP LOCKED`, checks for a BullMQ record by deterministic job ID, enqueues only if missing, and updates the PostgreSQL outbox state after Redis acknowledgement. A crash after Redis accepts the job but before PostgreSQL commit is reconciled against the retained Redis job. The dispatcher never processes editorial jobs itself.

The disposable GitHub Actions suite runs against PostgreSQL 17 and ACL-protected Redis, exercising idempotent queue creation, lost acknowledgements, Redis job disappearance, mismatched queue payload rejection, and terminal-job exclusion. These tests provide **at-least-once queue delivery**, not exactly-once processing. Redis/queue retention, actual research execution, least-privilege DB roles, explicit backup/restore procedures and data-profile deployment approval remain outstanding.

## Status reconciliation (CI-tested, not deployed)

The independently opt-in `apps/worker/src/status-sync.ts` polls retained BullMQ jobs and updates nonterminal PostgreSQL `vns.jobs` records under row locks. It maps Redis waiting to pending, active to running, delayed attempts to retry, completed to done, and terminal failed to failed. The attempt counter never decreases; raw stack traces and error details are never persisted (only `bullmq_failed`). Missing Redis jobs or mismatched job identifiers fail closed rather than inventing a success. Terminal PostgreSQL records cannot be overwritten by later queue snapshots. The last-20 authenticated dashboard listing already reads the `vns.jobs` statuses.

Integration tests use **synthetic editorial handlers in CI only**; the production worker still processes **probe only**. The reconciler never performs editorial work or starts automatically. Queue snapshots are eventually consistent, not atomic with PostgreSQL. They do not prove that a published video or external upload is complete, exactly-once side effects, or recovery after simultaneous Redis/PostgreSQL failure. Before activating any persistent infrastructure, apply reviewed least-privilege roles and a tested real backup/restore policy, plus explicit VPS deployment approval.

## Source provenance and manual review (offline)

Migration 0004 introduces `vns.research_evidence`: a citation URL, publisher,
headline and short claim associated with a specific research request. Its
initial status is **candidate**, not verified. A transition to `verified`,
`disputed` or `rejected` requires review metadata (reviewer and timestamp),
and a reviewed record cannot subsequently have its source or verdict silently
rewritten. Schema, constraints, evidence provenance and review states are tested
with disposable PostgreSQL and the restore drill.

`apps/worker/src/source-policy.ts` supplies a **pure, offline** source candidate
contract. It rejects obviously dangerous or malformed URLs and never verifies
a fact. These are lexical checks only: they **do not** make a URL safe to fetch.
Any future fetcher must enforce DNS resolution and IP range checks, redirect
restrictions, response size limits, timeout budgets, content safety, licensing
and editorial human review. No external source crawler is enabled; the normal
worker still processes probe only. A reviewer string in a database record is
metadata, **not proof of authentication**: production role/authorization gates
remain outstanding.

## Controlled HTTPS retrieval boundary (still disabled)

The new `apps/worker/src/source-fetch.ts` module provides a **separate,
opt-in** `VNS_SOURCE_FETCH_ENABLED=true` fetch policy requiring an explicit
comma-separated, exact hostname allowlist in `VNS_ALLOWED_SOURCE_HOSTS`.
It refuses IP-literal URLs and rejects mixed/private/loopback/link-local/
reserved DNS answers. Only public IPv4 endpoints may be contacted; the
checked IP is pinned into the HTTPS socket lookup, while the TLS hostname,
SNI and certificate validation remain bound to the allowed DNS hostname.
It uses native TLS, prohibits redirect following, disallows compressed,
binary or oversized responses, limits the response to 128 KiB, and returns a
SHA-256 digest with transient, UTF-8-decoded text for further _untrusted_
processing. No result can mark a factual claim `verified`.

The default production worker remains the **probe-only** entrypoint, and does
not import, enable or execute this fetcher. The module neither searches for
news sources nor submits real network requests in CI: tests inject a
synthetic DNS/response adapter and assert that unsafe hosts and DNS answers
cannot reach the requester, plus that the TLS options preserve origin
identity and IP pinning. The allowlist is not enabled in Docker Compose.

Before integration with any live research provider, independently review
source terms, attribution/copyright, allowed content types, redirected domains
(explicitly forbidden by current fetcher), health of source publishers,
network egress, DNS/timeouts, authenticated admin review, and whether a
brief digest/snippet should be stored as auditable provenance. `SourceDocument`
contains external untrusted text, not instructions for the assistant or a
basis for automatic factual validation. Passing the URL policy is not proof
that a source or its claims are reliable.


## Synthetic editorial research processor (offline integration, not deployed)

The new `apps/worker/src/research-process.ts` is an explicitly constructed
BullMQ processor, **not** the running `apps/worker/src/index.ts` entrypoint.
It refuses non-research job names, forged job IDs/payloads, missing PostgreSQL
research topics, zero or more than three candidate sources, duplicate sources
and invalid retrieval metadata. Source candidates come from an injected
provider. The injectable fetch port can later be wired to the separate
allowlisted, DNS-pinned HTTPS retrieval layer; no production provider or
source discovery adapter is installed yet.

The processor loads the authoritative topic from PostgreSQL, passes it to a
provider, validates candidates with `makeSourceCandidate`, retrieves each
source through the injected fetch port, and stores the source URL,
publisher, headline, claim and observed timestamp in
`vns.research_evidence` with database-default `review_status='candidate'`.
It never stores the fetched web page body, creates a verified verdict, updates
approval metadata, renders videos or publishes anything. If BullMQ retries a
job, the unique key `(job_id, source_url, claim_text)` makes writes idempotent:
an exact repeat preserves even an already reviewed record, while altered
publisher/headline metadata cause a fail-closed conflict.

CI builds the real worker code and runs a **synthetic** BullMQ research job
through Redis into a **disposable** PostgreSQL 17 database, then checks that
there is exactly one unverified provenance row, and that retries leave
existing reviewer decisions intact. This does not claim any external website
was queried or any report verified; the CI provider and fetched document are
synthetic. The running worker remains probe-only, and no source provider,
PostgreSQL credential or web access is enabled on the VPS.

Before live source discovery or editorial jobs may run, implement and review
trusted source discovery, explicit provider allowlists and rights policies,
authenticated human review, safe summarization and claim-to-source traceability,
auditable content digests, budget/rate limits, data recovery and least-privilege
DB credentials. A BullMQ `done` state describes processor completion,
**not** publication or fact verification.
