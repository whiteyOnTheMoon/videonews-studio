# P2-01 – Offline signed, atomic source publication and worker checkpoint

This increment extends the pure host-approved export from #243 with **an offline, unmounted Ed25519 publisher/consumer boundary**. The publisher receives a previously approved source bundle, a separately trusted host allowlist, and a private signing key provisioned out-of-band. It cannot create a new grant or discover sources; the cryptographic signature establishes that the **specific** bundle was issued by its private key holder, rather than treating its integrity-only SHA-256 as authority. The worker side requires the **pinned separate Ed25519 public key** and its own independently trusted HTTPS host allowlist, and still validates every source and blocked/pending child scope.

Both sides use a caller-provisioned, private (0700), canonical, owned directory, with symlink- and permission-checked inputs, bounded files, exclusive lock directories, temp files created with 0600 and O_EXCL/O_NOFOLLOW, file fsync, atomic same-directory rename and directory fsync. A stale lock after a crash deliberately blocks automatic continuation and requires operator recovery. Atomicity applies to the individual published export file and the individual consumer checkpoint file. The consumer commits the new high-water checkpoint **before** returning a source list; if it is absent, initial acceptance requires an explicit operator bootstrap, never an implicit reset.

A consumer checkpoint stores signed-envelope digest, source revision and independent host approval revision, checks that both revisions are nondecreasing, and forbids a *different* signed payload at identical revisions. A publisher also rejects older/equivocating revisions. Synthetic tempfile tests exercise signatures, independent host authorization, file permissions, manual bootstrap, restart readback, replay, same-revision equivocation, stale locks and symlink inputs.

**Important security boundary:** These checks detect replay while the worker-owned checkpoint remains intact. An attacker able to replace **both** signed export and worker checkpoint with a previously valid pair, or a privileged operator intentionally resetting the checkpoint, can roll back the local monotonic state. Cryptography on the bundle alone cannot eliminate this. Production must anchor the high-water mark in a separately protected monotonic store, manage signing-key rotation and recovery/backup procedures, and prove publisher/consumer filesystem user isolation.

This is not mounted in `apps/worker/src/index.ts` or any scheduler/API entrypoint. No directory path, private key, live source, DB credential, new runtime permission, background task or external request is provisioned. Do **not** enable feed fetching based solely on this offline module. Remaining approval gates include independent human review/rights, controlled integration, external high-water persistence and #17 end-to-end scheduler acceptance.
